# requirements-clock.txt -- Clock-Authority zone-resolution deps (v9.12.0, FEAT-CLOCKAUTHORITY-9.12.0-001)
#
# Governing contract: docs/superpowers/specs/2026-08-04-clock-authority-adr.md
# (revision 6) decision D4.4. Backs `.protocol-state/time_provider.py`'s
# `TimeProvider.resolve_user_zone()` OS-fallback tier (D4.1.3) and the
# `zoneinfo.ZoneInfo(...)` resolution every tier (config/env/OS-fallback)

#
# Install with:
#   pip install --require-hashes -r requirements-clock.txt
#
# SCOPE / WHY THIS IS A SEPARATE FILE: CPython's stdlib `zoneinfo` module
# (3.9+, already this project's floor) needs an IANA tzdata SOURCE to resolve
# a *known* zone name to UTC-offset rules. Most POSIX systems ship one at
# `/usr/share/zoneinfo`; Windows does not ship one at all -- so on a fresh
# Windows install, EVERY `zoneinfo.ZoneInfo("America/Detroit")`-style call
# raises `ZoneInfoNotFoundError`, regardless of how correct the IANA name is
# (verified during A2 implementation: a real Windows dev box with no
# `tzdata` package installed rejects every valid IANA zone name it is asked
# to resolve, including via `protocol.config.yaml::user.timezone`). This is
# ADR D4.4 "problem 1". Separately, Windows does not natively expose an IANA
# zone name for its OWN configured OS zone (D4.4 "problem 2") -- `tzlocal` is
# the OS-zone-detection dependency the ADR names for that path, used ONLY by
# `TimeProvider._detect_os_zone()`'s OS-fallback tier (D4.1.3), never by the
# config/env tiers (which already carry a validated IANA name and only need
# `tzdata`'s data, not `tzlocal`'s detection).
#
# THESE ARE CONSUMER-FACING RUNTIME DEPENDENCIES, not dev/CI-only tooling
# (unlike requirements-test.txt, which is pytest-for-CI only and explicitly
# excluded from the publish manifest -- see that file's own header). Every
# consumer install that resolves a user-facing local time through
# `TimeProvider` needs `zoneinfo` to actually find zone data, which on
# Windows means needing `tzdata` installed. Both packages are therefore
# listed in `scripts/distro/publish-manifest.yaml::include_files` alongside
# `requirements-dev.txt`/`requirements-enc.txt` (added in the same commit
# that introduces this file, per the ADR's A2 Definition-of-Done and this
# repo's manifest-completeness lesson -- see CLAUDE.md's "Distro manifest
# completeness" guidance and `distro-manifest-completeness` memory).
#
# `tzdata` is pinned WITHOUT a platform marker (installed on every platform,
# not just Windows) even though POSIX hosts usually already have a system
# zoneinfo tree, because "usually" is not "always" (minimal containers and
# some POSIX distributions ship no system tzdata either) and the package is
# a small, pure-data, zero-native-code, PSF-license-compatible dependency --
# the defensive `try: import tzdata` gate in `time_provider.py` means its
# presence is never assumed, only opportunistically used when installed via
# this file.
#
# HASH-PIN POLICY: same convention as requirements-test.txt / requirements-enc.txt
# (C2-5, v9.9.1, SEC-CORTEX-ENC-HASH-001 -- OWASP A06:2021 defense-in-depth).

# --hash=sha256:... entry per file (wheel + sdist) PyPI published for that
# release. This enables `pip install --require-hashes -r requirements-clock.txt`,
# which refuses to install anything whose downloaded artifact does not match
# a pinned digest -- protection against a compromised/typosquatted package or
# a tampered mirror.
